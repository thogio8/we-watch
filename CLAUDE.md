# WeWatch

Appli pour un couple : on swipe des films TMDB dans une liste « à voir », puis le soir un tirage au sort choisit le film (avec filtres « ce soir » : heure de coucher, humeur, plateformes). PWA installable (iPhone, Android, ordinateur). Depuis la 2.0, chacun a son compte (Better Auth), créé et ouvert avec une passkey (Face ID, empreinte ou code du téléphone) : plus de code d'accès partagé, pas de mot de passe, aucun email envoyé. Chaque liste appartient à un **groupe** (le couple d'origine est le groupe hérité « NOUS DEUX ») : la pastille en haut de TIRER, SWIPER et LISTE change le groupe affiché ou en crée un, et mène à « MEMBRES ET INVITATION » (`/groupe` : renommer, lien d'invitation, retirer un membre, quitter). On rejoint un groupe par son lien d'invitation (`/invitation/<jeton>`), compte compris si on n'en a pas. Le panneau de la pastille mène aussi à « MON COMPTE » (`/compte`, sans pastille) : changer son prénom, ses clés d'accès (en ajouter une depuis cet appareil, en supprimer, jamais la dernière), ses appareils connectés (en déconnecter un), se déconnecter, supprimer son compte (en tapant son prénom). Pas un produit commercial (licences TMDB / Vercel Hobby non commerciales).

- Prod : Vercel (région des fonctions dans `vercel.json`, au plus près de la base) + base Turso (libSQL). L'adresse de prod est la variable de dépôt GitHub `PROD_URL` (`gh variable list`), jamais écrite en dur.
- Specs de référence, versions comprises : `docs/superpowers/specs/2026-10-23-we-watch-design.md` (§1-10 V1/V1.1, §11 V1.2, §12 V1.2.1, §13 V1.2.2+), complétée pour la 2.0 (comptes, groupes) par `docs/superpowers/specs/2026-10-28-wewatch-v2-design.md`, qui prime sur ce qu'elle change. **Les lire avant toute fonctionnalité** et ajouter une section pour chaque nouvelle version.

## Pièges connus (déjà mordus)

- **`npm start` se branche sur la base de PROD** : en mode production, Next charge `.env.production.local` (secrets Turso). Pour tester un build en local, toujours `npm run start:local`.
- **Push sur `main` = mise en prod, mais seulement via GitHub Actions** (`.github/workflows/ci.yml`) : trois jobs en parallèle (`checks` = `npm run ci:checks`, `e2e` = `npm run test:e2e`, `build` = déploiement Vercel construit et envoyé **sans être mis en ligne**, `--skip-domain`), puis, tous verts, `release` : sauvegarde chiffrée (voir « Sauvegarde chiffrée »), migration Turso, mise en ligne du déploiement construit (`scripts/vercel-prod.sh promote`, qui attend jusqu'à 3 minutes que la prod serve vraiment ce déploiement, pour que la fumée ne teste pas l'ancien ; chaque requête à Vercel est bornée à 30 s, et le job a 25 minutes, de quoi couvrir le pire cas borné retour arrière compris : un job annulé sauterait le retour arrière, `tests/scripts/release-budget.test.ts`), test de fumée (`scripts/smoke-prod.sh`, qui attend d'abord, jusqu'à 2 minutes, que `/connexion` réponde 200 : Vercel peut annoncer la mise en ligne avant que le domaine ne serve le nouveau déploiement), et retour arrière automatique si la fumée échoue. La fumée vérifie, sans jamais afficher un corps de réponse ni un secret : `/connexion` 200 ; `/` 307 vers `/connexion` ; une CSP avec `frame-ancestors 'none'` ; l'inscription sur invitation (`/connexion` affiche `CLOSED_ERROR` de `src/features/signin/messages.ts`, rendu par `SigninHome` ; `tests/scripts/smoke-prod.test.ts` garde le texte du script égal à cette constante ; variable de dépôt facultative `EXPECT_SIGNUP`, `invite` par défaut, `open` pour sauter ce contrôle) ; les options de connexion passkey en 200 avec `"rpId"` = l'hôte de `PROD_URL` (donc `BETTER_AUTH_URL` dans Vercel = `PROD_URL` au caractère près, sinon fumée rouge et retour arrière) ; `/api/auth/ok` 404 ; un POST d'une autre origine sur `verify-authentication` refusé en 403 ; le cron (ménage puis rafraîchissement) en 200 sans film en échec. L'auto-deploy Git de Vercel est coupé (`vercel.json`). Ne jamais déployer à la main (`vercel --prod`) ni migrer la prod à la main. Chaque secret de la CI est posé sur la seule étape qui s'en sert, jamais dans l'`env` d'un job ni sur `npm ci` (le code des dépendances ne le voit pas ; `release` installe avec `--ignore-scripts`) ; la CLI Vercel est une devDependency à version exacte (`npx --no vercel`, jamais téléchargée au run, Dependabot la monte). Le jeton du workflow est en lecture seule par défaut (`permissions: contents: read` ; seul le job `version` l'élargit) et chaque action est épinglée par le SHA de son commit, la version en commentaire (Dependabot `github-actions` monte les deux). Risque accepté (`docs/security-audit-2.0.md`, M1) : `vercel build` exécute le code des dépendances avec les variables de prod.
- **Migrations rétrocompatibles** : la migration passe _avant_ le nouveau code, pendant que l'ancien sert encore. Ajouter des colonnes (nullables ou avec défaut), jamais renommer ni supprimer dans la même version ; supprimer dans une version suivante. Groupes (2.0) : `0005` crée les tables, `0006` copie `movies` dans le groupe hérité « NOUS DEUX » (`LEGACY_GROUP_ID`, créé seulement si `movies` a des lignes, sans membre), `0007` distingue « copié » (`legacy` : personne n'a ajouté le film) de « vu avant les comptes » (`watched_legacy` : personne ne l'a marqué ; « marquer vu » l'efface, et un marqueur dont le compte disparaît devient « un ancien membre ») ; `movies` n'est plus écrite mais reste intacte pour un retour en 1.3.x. Invitations : `0008` ajoute `app_group.invite_token` (nullable, index unique). Limites : `0010` crée la table `rate_limit` (nouvelle table seule). Rattrapage : `0011` rejoue dans « NOUS DEUX » ce que la 1.3.x a écrit dans `movies` pendant le retour arrière de la bascule (2026-11-03, `scripts/replay-legacy-movies.sql`, idempotent).
- **Aucune migration sur `main` avant la bascule de la 2.0** (morceau 6) : drizzle ignore une migration dont l'horodatage précède la dernière appliquée en prod, donc une migration poussée sur `main` pendant que la branche 2.0 en garde de plus anciennes ferait sauter ces dernières.
- **Next 16 ≠ ce que tu connais** (voir AGENTS.md) : `src/proxy.ts` remplace `middleware`, `cacheComponents` est actif (tout accès à `searchParams`, `cookies()`, `connection()` doit être sous un `<Suspense>`, sinon le build échoue), `PageProps<"/route">` est global. Sur une route dynamique (`/list/[tmdbId]`), passer la promesse `params` à un composant sous `<Suspense>`, et tout composant client qui lit l'URL (`usePathname`) doit aussi être sous `<Suspense>` : c'est pourquoi `BottomNav` l'est dans le layout.
- **Variables Vercel lues au build : jamais « Sensitive »** : `vercel pull` écrit `[SENSITIVE]` à la place d'une variable sensible, et le client Better Auth lit `BETTER_AUTH_URL` au pré-rendu (`authClient`) ; `BETTER_AUTH_URL` et `SIGNUP` sont donc des variables lisibles (`vercel env add … --no-sensitive`), les secrets (`BETTER_AUTH_SECRET`, `OWNER_CODE`, `CRON_SECRET`, base, TMDB) restent sensibles et ne servent qu'à l'exécution.
- **Le proxy valide l'environnement à chaque requête** : une variable invalide (ex. `CRON_SECRET` < 16 caractères) met **tout** en 500, `/connexion` comprise.
- **Sans session, tout renvoie vers `/connexion`** (pages) ou répond 401 (actions serveur) : le proxy lit la session Better Auth (cache signé de 5 minutes dans un cookie, sinon la base). Seuls `/connexion`, `/api/auth/*`, `/invitation/*` (lien d'invitation : la page **et toutes les actions serveur**, d'où `assertSignedIn` dans chacune sauf `prepareSignup`, vérifié par le méta-test `tests/functional/server-actions.test.ts` sur tout module `"use server"` de `src`, où la directive n'est permise qu'en tête de fichier ; chaque action y reçoit des arguments plausibles, table `ARGUMENTS`), les fichiers publics et le cron (son `CRON_SECRET`) passent sans. Seuls les chemins Better Auth de `AUTH_PATHS` (`src/auth/auth-paths.ts` : `/sign-out` et les quatre étapes des cérémonies passkey) répondent ; tout autre chemin sous `/api/auth` répond 404 (plugin `onlyAuthPaths`, premier de la liste, testé sur chaque route de `auth.api` par `tests/functional/auth-paths.test.ts`), `/get-session`, `/ok`, `/callback/:id` et la gestion des sessions compris : l'appli lit la session par `auth.api` (que le plugin ne voit pas) et gère les sessions par ses propres actions serveur. En production, le contrôle d'origine et CSRF de Better Auth est forcé (`originCheckForcedOn`, `src/auth/create-auth.ts`) : sinon une variable `TEST` le couperait ; la fumée le vérifie (POST d'une autre origine → 403). Un chemin coupé n'écrit rien dans `rate_limit` (règle `"/**"`, `src/auth/rate-limits.ts`). Un nouveau chemin utilisé par le client (Google, morceau 4) s'ajoute d'une ligne à `AUTH_PATHS`. Les passkeys sont liées au nom d'hôte de `BETTER_AUTH_URL` (`rpID`) : changer d'adresse rend les passkeys existantes inutilisables. Une passkey s'ajoute connecté par la même cérémonie que l'inscription : `src/auth/passkey-registration.ts` fixe côté serveur son nom (l'appareil, `deviceLabel`), n'ouvre de session qu'à l'inscription et met le prénom dans le trousseau ; `afterVerification` (`passkey-signup.ts`) relit la session en base (`getAuthoritativeSessionFromCtx`), donc une session révoquée n'ajoute rien ; le plugin, lui, se fie au cache : sur une session révoquée, les hooks `before` de `/passkey/generate-register-options` et `/passkey/verify-registration` retirent les cookies de session de la requête, pour qu'une inscription avec ticket sur cet appareil crée son compte normalement. La dernière passkey ne se supprime pas (une seule requête, `src/db/account.ts`).
- **Seul le proxy laisse passer une session supprimée, jusqu'à 5 minutes** (avec les pages déjà en cache sur l'appareil, qui ne peuvent plus rien changer) : il se fie au cookie de cache (`better-auth.session_data`, `cookieCache` dans `src/auth/create-auth.ts`) tant qu'il est valide. Pages et actions, elles, relisent la base à chaque fois (`getCurrentUser` dans `server/session.ts`, `AUTHORITATIVE_SESSION_READ` : `disableCookieCache` et `disableRefresh`) : une session révoquée ailleurs (« DÉCONNECTER » un appareil dans « MON COMPTE ») voit ses actions refusées aussitôt, et une page pas encore en cache côté client (`getActiveGroup`, ou `/compte` sans session) renvoie vers `/connexion`, même sur une navigation côté client et cookie de cache encore valide (scénario e2e « déconnecter un autre appareil… ») ; une page déjà en cache sur l'appareil (`staleTimes`, voir plus bas) peut encore s'afficher jusqu'à 5 minutes. Un refus d'action faute de session porte un `digest` (`signedOutRefusal`, `src/access/signed-out.ts`), seul détail que Next transmet au client en prod : chaque `catch` d'action côté client appelle `leaveIfSignedOut(error)`, qui recharge `/connexion` (et `app/error.tsx` pour ce que rien n'attrape) ; à garder sur tout nouvel appel d'action (scénario e2e « un appareil déconnecté ailleurs, sur une page déjà affichée… »). Cette lecture n'écrit **aucun cookie** : Next re-rend toute la page après une action qui pose un cookie, et l'écran MEMBRES (qui demande son lien d'invitation une fois monté) bouclait ; c'est le proxy qui prolonge la session et son cache, mais pas sur une navigation côté client (en-tête `RSC: 1` sans action, que `nextCookies()` exclut du rafraîchissement) : le renouvellement vient des chargements complets et des POST d'actions, donc ne pas « optimiser » le proxy pour qu'il ne lise la session que sur les actions. Les fichiers SQLite locaux (dev, tests, e2e) attendent jusqu'à 5 s un verrou tenu par un autre processus (`timeout` dans `src/db/create-database.ts`) au lieu d'échouer en `SQLITE_BUSY`.
- **Groupe affiché = cookie `ww_group`** (`GROUP_COOKIE`, `domain/group.ts` ; `httpOnly`, 400 jours, `secure` dès que `BETTER_AUTH_URL` est en https : attributs donnés par `groupCookieAttributes(baseURL)`, seule source, à chaque écriture comme à chaque effacement) : `getActiveGroup()` (`server/groups.ts`) ne le croit que si j'en suis membre, sinon prend mon groupe au `last_used_at` le plus récent ; aucun groupe → écran « CRÉER TON PREMIER GROUPE » ; sans session → `redirect("/connexion")`. Il lit `cookies()` : toujours sous `<Suspense>`, après `connection()`. Seules `createGroup`, `chooseGroup` et `joinGroup` l'écrivent (`rememberGroup`) ; quitter ou se retirer l'efface s'il désigne ce groupe (`forgetGroup`) ; se déconnecter l'efface toujours (hook `after` de `/sign-out` dans `src/auth/create-auth.ts`), pour qu'un autre compte sur le même appareil n'en hérite pas ; déconnecter cet appareil depuis « MON COMPTE » ou supprimer son compte l'efface aussi, avec les cookies de session (`signOutThisDevice`, `server/sign-out.ts`), puis le client va sur `/connexion`. **Aucune autre action ne lit le cookie** : la page lie le groupe affiché (`action.bind(null, group.id)`), pour qu'un changement de groupe dans un autre onglet n'écrive pas dans le mauvais groupe.
- **Le téléphone garde les pages visitées 5 minutes** (`staleTimes` dans `next.config.ts`) : toute action serveur qui modifie la base doit appeler `revalidateListPages()` (`src/server/revalidate.ts`), sinon TIRER et LISTE affichent une donnée périmée (test e2e « une page déjà visitée… ») ; une action qui change le groupe affiché (créer, choisir) ou sa pastille appelle `revalidateGroupPages()`, qui périme aussi SWIPER (jamais pendant un swipe : la pile se rechargerait). Membres : renommer → `revalidateGroupPages()` ; rejoindre, quitter, retirer → `revalidateGroupPages()` + `revalidatePath("/groupe")` ; régénérer le lien → `revalidatePath("/groupe")` seul (test e2e « renommer le groupe change la pastille… »). Après avoir quitté, l'écran recharge `/` en entier (`window.location.replace`). Mesurer la navigation : `SESSION_TOKEN=… node scripts/measure-nav.mjs <url>`, avec la valeur du cookie `better-auth.session_token` (`__Secure-…` en https) copiée depuis son propre navigateur connecté (un navigateur sans écran n'a pas de passkey) ; le script ne l'affiche jamais.
- **Lien d'invitation = secret** : jeton de 32 octets aléatoires en base64url (43 caractères), dans `app_group.invite_token`, créé à la première demande (`ensureInvite`, idempotent : `UPDATE … WHERE invite_token IS NULL`, appelé par l'écran une fois monté, jamais au rendu serveur) ; « RÉGÉNÉRER » le remplace (l'ancien lien ne marche plus). Lien = `${BETTER_AUTH_URL}/invitation/<jeton>` (l'origine vient de l'environnement, jamais de la requête). **Un seul résolveur** : `findInvitedGroup` (`server/invitations.ts`) ; un jeton qui ne correspond pas à `isInviteToken` (`domain/group.ts`) répond « CE LIEN N’EST PLUS VALABLE » sans lire la base. Le jeton ne vit que dans le chemin : jamais dans le ticket d'inscription (qui porte l'id du groupe), une query string ni un log ; `Referrer-Policy: no-referrer` sur `/invitation/:token*` (`next.config.ts`). La page `/invitation/[token]` (`features/invitation/`, `loadInvitation`) a quatre états : invalide, déconnecté (connexion en variante invitation : « CRÉER UN COMPTE » même en mode `invite`, et le compte créé rejoint le groupe dans la transaction d'inscription), « REJOINDRE », « Y ALLER » (déjà membre : bascule comme `chooseGroup`).
- **Rejoindre et partir sans course** (`db/membership.ts`) : `join` est un seul `INSERT … SELECT … WHERE EXISTS (groupe) ON CONFLICT DO NOTHING` (`"joined" | "already" | "gone"`) ; `leave` est une **transaction explicite** : supprime l'appartenance et ses « voulu » du groupe, puis, si plus personne n'est membre, `movie_want`, `group_movie` et `app_group` par des `DELETE … WHERE NOT EXISTS (membership)`, jamais en comptant d'abord. Ne pas compter sur les cascades (clés étrangères peut-être coupées) : enfants supprimés explicitement. Les BOF sont personnels (`movie_rejection` sans groupe) et restent ; ajouts et « marqué par » aussi.
- **Supprimer un compte = une transaction** (`db/account-deletion.ts`, `deleteUserIn`) : `leaveIn` (`db/membership.ts`, la même que `leave`) pour chacun de ses groupes (ses « voulu » partent, le groupe aussi s'il se vide), puis tous ses `movie_want` (filet) et ses BOF, `added_by` / `watched_by` mis à `NULL` explicitement (ses films restent aux autres, « ajouté par un ancien membre »), ses passkeys, sessions, comptes et l'utilisateur. Chaque suppression filtre sur cet utilisateur, sans compter sur les cascades. L'action `deleteAccount` exige le prénom exact (`confirmsName` : NFC, espaces et apostrophes repliés, casse exacte), vérifié aussi côté client avant d'activer « SUPPRIMER DÉFINITIVEMENT ». Les index de `0009` (`movie_want.user_id`, `group_movie.added_by`, `group_movie.watched_by`) servent cette suppression.
- **En-têtes de sécurité sur toute réponse** (`next.config.ts`, règle `/:path*`, avant celle de `/invitation/:token*` qui garde `no-referrer` : pour une même clé, la dernière règle gagne) : CSP **statique** (`'unsafe-inline'` pour les scripts de Next, car un nonce exige un rendu par requête, incompatible avec `cacheComponents` ; `'unsafe-eval'` en dev seulement ; images : `'self'`, `data:`, `blob:` et `https://image.tmdb.org`, qui doit suivre `images.remotePatterns`), `nosniff`, `X-Frame-Options: DENY`, COOP, `Permissions-Policy`, HSTS. Toute nouvelle ressource externe (image, script, iframe, appel `fetch` côté client) doit y entrer, sinon le navigateur la bloque : en e2e, toute violation CSP ou tout 404 sous `/api/auth/*` fait échouer le test (`e2e/csp.ts` : console du navigateur et événement `securitypolicyviolation` ; branché sur chaque contexte de navigateur par `e2e/fixtures.ts`, seconds appareils compris ; `e2e/csp-watcher.spec.ts` prouve qu'il attrape une violation). La barre d'outils Vercel des déploiements de preview (scripts de `vercel.live`) est bloquée par la CSP, exprès : ne pas élargir la CSP pour elle. Valeurs vérifiées par `tests/next-config.test.ts`. `poweredByHeader: false` : pas d'en-tête `X-Powered-By: Next.js`.
- **Limites de tentatives** : fenêtre fixe, comptée **avant** toute validation (une tentative invalide compte aussi), dans la table `rate_limit` (migration `0010`) par une seule requête `INSERT … ON CONFLICT DO UPDATE … RETURNING` (`db/rate-limit.ts` : pas de lecture puis écriture, donc pas de course). Un refus est un **résultat** (« TROP D’ESSAIS. RÉESSAIE DANS UN MOMENT. », `TOO_MANY_ATTEMPTS`, ou `reason: "too_many"` pour `deletePasskey`), jamais une exception ; une cérémonie passkey refusée en 429 côté client affiche le même texte (`isTooManyAttempts`). **Ordre dans une Server Action : session (et appartenance), puis limite, puis validation** : `withinLimit(name, subject)` (`server/rate-limit.ts`) juste après `assertSignedIn` / `assertMember`, par utilisateur (`create-group`, `join-group`, `rename-me`, `delete-passkey`, `delete-account`). `prepareSignup`, sans session, compte `signup:<ip>` en premier, puis `owner-code:<ip>` seulement si un code est saisi, juste avant de le comparer. Les valeurs sont une table, `ACTION_LIMITS` (`src/domain/rate-limit.ts`) : **toute nouvelle action d'écriture exposée** y prend une ligne et appelle `withinLimit`, sauf choix dit (non limitées : `revokeSession`, `renameGroup`, `regenerateInviteLink`, `removeMember`, `leaveGroup`, `chooseGroup` : réservées aux membres ou à soi, idempotentes, rien à deviner) ; aucun seau commun à toutes les IP (une attaque bloquerait le code propriétaire). Better Auth : `rateLimit` actif partout, tests compris (`authRateLimit`, `src/auth/rate-limits.ts`), compté dans la même table (`customStorage`) sous `ip|chemin` : 100 par minute par défaut, plus strict sur les quatre chemins passkey (`AUTH_RATE_RULES`), puis la règle `"/**"` en dernier, qui ne compte que les chemins de `AUTH_PATHS` (un chemin inconnu n'écrit rien). IP : `clientIp()` la lit comme Better Auth (`getIP`, qui n'accepte qu'un `x-forwarded-for` à une seule valeur, celui que Vercel réécrit) ; sans IP de confiance, la clé partagée `no-trusted-ip`, la même que Better Auth (après la bascule, aucune ligne « Rate limiting could not determine a client IP » ne doit apparaître dans les journaux Vercel). Tests : les tests unitaires des actions font `vi.mock("@/server/rate-limit")` (`src/server/__mocks__/rate-limit.ts` : tout permis, IP fixe ; `signin/actions.test.ts` passe sa propre fabrique) et prouvent l'ordre avec `expectLimitedFirst` (`tests/helpers/limited.ts`) ; les fonctionnels gardent les vraies limites : `reset` de `startServerStack` vide `rate_limit`, et un fichier qui assemble son propre Better Auth le vide dans un `beforeEach`. `tests/functional/no-client-ip.test.ts` supprime `NODE_ENV` dans `vi.hoisted` (sous test, Better Auth prendrait `127.0.0.1`) : cela ne marche que parce que Vitest isole chaque fichier (son défaut), donc jamais `isolate: false`.
- **Cron quotidien** (`vercel.json`, `/api/cron/refresh-movies`, protégé par `CRON_SECRET`) : d'abord le **ménage** (`db/housekeeping.ts`, un seul lot) : `verification` expirées, `session` expirées, `signup_ticket_use` de plus de 15 min (le ticket vit 10 min), `rate_limit` dont la fenêtre a commencé il y a plus de 24 h ; aucune de ces lignes n'est un parent. Puis le rafraîchissement TMDB. Un ménage qui échoue lève (500) : une base cassée fait échouer le cron et la fumée. Le rapport (`purged` compris) va dans les journaux Vercel.
- **Sauvegarde chiffrée** (job `release`, avant la migration) : `scripts/backup-db.mjs` lit les tables de `TABLES` (`scripts/backup-tables.mjs`, dans l'ordre des clés étrangères, celui de la restauration) en **un seul lot en lecture** (un instantané cohérent : la prod sert pendant la sauvegarde) : listes, groupes, instantanés TMDB, `movies`, `user`, `passkey` (clés publiques) et `account` **sans** `access_token`, `refresh_token`, `id_token` ni `password` ; jamais `session`, `verification`, `signup_ticket_use` ni `rate_limit`. Une table absente est sautée (base 1.3.x : `movies` seule). Puis AES-256-GCM (`scripts/backup-crypto.mjs`) avec `BACKUP_KEY` (64 caractères hexadécimaux, secret GitHub posé sur cette seule étape, copie hors ligne chez le mainteneur, gardée 90 jours après un changement de clé) → artefact `backup/db.json.enc`, 90 jours. Sans clé valide, le script échoue avant de lire la base, sans repli en clair : ni migration ni mise en ligne. Il n'affiche que des comptes de lignes. Une nouvelle table de l'appli s'ajoute à `TABLES` à sa place (aucun test ne le rattrape), sauf secrets ou tenue de compte. Autour : `scripts/read-backup.mjs` lit tout format gardé par la CI (`movies.json` de la 1.3.x, `db.json`, `db.json.enc`) ; `scripts/restore-db.mjs` restaure dans une base neuve, migrée et vide, en une transaction (refuse une sauvegarde d'avant 2.0) ; `scripts/rehearse-migration.mjs` répète la migration 2.0 sur une sauvegarde 1.3.x (`--db <cible>`, `--probe`) ; `scripts/replay-legacy-movies.sql` rattrape ce que la 1.3.x a écrit après un retour arrière (livré en migration, jamais lancé à la main). Le déroulé (bascule, retour arrière, restauration) : `docs/bascule-2.0.md`.
- **Clés étrangères sur Turso** : `PRAGMA foreign_keys` de la prod n'est pas connu (vérification facultative, en lecture seule, dans `docs/bascule-2.0.md` §3 : `rehearse-migration.mjs --probe`), donc le code ne compte **jamais** sur une cascade : `leave` / `leaveIn` (`db/membership.ts`) et `deleteUserIn` (`db/account-deletion.ts`) suppriment chaque enfant explicitement, la suppression d'une passkey (`db/account.ts`) n'a pas d'enfant, le ménage du cron ne purge aucun parent, la restauration insère dans l'ordre des clés et la répétition vérifie `foreign_key_check`. Les `onDelete: "cascade"` du schéma ne sont qu'un filet.
- **Caractères invisibles bruts interdits** dans `src`, `tests` et `e2e` (`tests/source-hygiene.test.ts`, contre le Trojan Source) : écrire `\u200B`, `\u2066`… en échappement.
- Ne jamais afficher ni committer `BETTER_AUTH_SECRET`, `OWNER_CODE`, `CRON_SECRET`, `BACKUP_KEY`, un jeton de session, les jetons TMDB / Turso (ni `ACCESS_CODE`, gardé dans Vercel jusqu'en 2.1 pour un retour arrière vers la 1.3.x).

## Architecture

```
src/
  domain/    règles métier PURES (aucun import hors domain) : films, transitions de statut, tirage, filtres « ce soir », groupes (nom, cookie), attribution (« voulu par… »), appareil (`deviceLabel`)
  db/        Drizzle (dépend de domain) : schema.ts (movies, gelée depuis la 2.0) + auth-schema.ts + group-schema.ts (app_group, membership, group_movie, movie_want, movie_rejection, movie_snapshot) + rate-limit-schema.ts (rate_limit) ; dépôts snapshots (données TMDB partagées), group-list (liste d'un groupe + list-queries), decisions (swipes : « voulu par », BOF personnels, pile), groups (mes groupes) + membership (rejoindre, membres, partir) + invitations (jetons), account (« MON COMPTE » : mes passkeys, mes sessions) + rate-limit (compteur de tentatives) + housekeeping (ménage du cron) + account-deletion (supprimer un compte : `leaveIn` de chaque groupe puis tout ce qui est à lui seul, en une transaction, sans compter sur les clés étrangères)
  tmdb/      client TMDB + schémas zod + mapping + decks thématiques (dépend de domain)
  auth/      Better Auth : configuration (passkeys, session, chemins ouverts `AUTH_PATHS`, limites `rate-limits.ts`), création de compte par passkey (ticket signé : nom, propriétaire, groupe de l'invitation), group-join.ts (le nouveau compte rejoint le groupe de l'invitation, affiché, et « NOUS DEUX » s'il est propriétaire, par un insert conditionnel dans la transaction d'inscription, que signup-transaction.ts expose)
  access/    qui entre : décision du proxy, session lue, droit d'inscription (SIGNUP, OWNER_CODE), ticket d'inscription signé, secret du cron
  server/    container.ts : SEUL endroit qui assemble base, TMDB, dépôts et Better Auth ; session.ts : utilisateur courant ; sign-out.ts : déconnecter cet appareil quand sa session disparaît (cookies de session, `__Secure-` en https, et `ww_group`) ; groups.ts : groupe affiché (getActiveGroup, rememberGroup, forgetGroup), appartenance (assertMember, isMemberOf) ; invitations.ts : le jeton d'un lien → son groupe (findInvitedGroup) ; rate-limit.ts : limites des actions (withinLimit, clientIp)
  features/  un dossier par écran : composants, actions serveur, logique locale testée (groups : pastille et actions de groupe ; group-members : « MEMBRES ET INVITATION » ; invitation : la page du lien)
  ui/        composants partagés sans logique métier (Ticket, Button, Chip, Stamp…)
  styles/    tokens.css : SEUL fichier autorisé à contenir couleurs, ombres, rayons
  app/       routes Next (pages fines : lecture des données + Suspense), API cron, icônes PWA
```

Règles :

- **Sens des dépendances** : `domain` ← `db`/`tmdb` ← `server` ← `features` ← `app`. `access` ne dépend que de `domain` (et de l'env) ; `auth` de `domain`, `db` et `access` ; seul `server` assemble Better Auth. Un composant client n'importe jamais un module serveur : la page lui passe les actions serveur en props.
- Modules serveur marqués `import "server-only"`.
- **Server Actions** = endpoints publics : chacune commence par `await assertSignedIn()` (`server/session.ts`), ou, si elle porte sur un groupe, par `await assertMember(groupId)` (`server/groups.ts` : session **et** appartenance ; le `groupId` arrive en premier argument, lié par la page au groupe affiché, jamais lu dans le cookie), puis, si c'est une écriture que `ACTION_LIMITS` prévoit, `await withinLimit(…)` (voir « Limites de tentatives »), puis valide ses arguments ; un `groupId` forgé ou d'un autre groupe est refusé avant toute lecture ou écriture. Une page lit le groupe affiché avec `getActiveGroup()` (sous `<Suspense>`, après `connection()`). Convention d'erreur : une **lecture** qui dépend de TMDB renvoie `{ ok: false }` (panne attendue, affichée dans la DA) ; une **écriture** lève une exception sur une panne (le client la rattrape et affiche un message générique « PAS RÉUSSI…, RÉESSAIE ») ; un **refus attendu** d'une écriture est un résultat (`{ ok: false, error }` à afficher, ou `{ ok: false, reason }` que le client traduit : `deletePasskey` distingue `"last"` de `"not_found"`), jamais une exception, pour qu'une coupure réseau ne s'affiche pas comme « CETTE CLÉ N’EXISTE DÉJÀ PLUS ».
- Logique non triviale = fonction pure dans `domain/` ou `features/x/*.ts`, testée à part ; les composants restent de l'affichage.
- Ces règles de couches sont **vérifiées par ESLint** (`eslint.config.mjs`, `no-restricted-imports`) : un import interdit casse la CI.

## Code propre : SOLID, KISS, DRY (non négociable)

Concrètement, sur ce repo :

- **Une responsabilité par fichier** (S). Un écran = un composant qui assemble ; l'état et les effets vont dans un hook `useX.ts`, la logique dans un `.ts` pur testé, chaque vue/morceau d'UI dans son composant. Modèles à suivre : `features/draw/` (`useDraw` + `drawView` + `DrawHome`/`DrawResult`…), `features/swipe/` (`deckState` reducer + hooks + sous-composants).
- **Ouvert à l'extension** (O) : préférer une table de données à un `switch` qui grossit (`TRANSITIONS` dans `domain/transitions.ts`, `DECKS`, `MOODS`, handlers du reducer de `deckState.ts`).
- **Dépendre d'interfaces** (D) : les features déclarent leurs ports (`DeckDeps`, `RefreshDeps`), `server/container.ts` les implémente ; les composants reçoivent les actions serveur en props.
- **KISS** : pas d'abstraction « au cas où », pas de framework maison, pas de dépendance pour trois lignes. Le plus simple qui passe les tests.
- **DRY** : avant d'écrire, chercher l'existant. Briques partagées :
  - UI : `ui/Headline` (titres riso), `ui/cx` (classes), `ui/Tab.module.css` (onglets, via `composes`), `ui/Ticket`, `ui/TicketDetails`, `ui/Button`, `ui/Chip`, `ui/Stamp`, `ui/Lines`, `ui/ConfirmButton` + `ui/useConfirm` (action destructive confirmée dans un ticket de la DA, jamais `window.confirm` ; `ready` + un champ en enfant pour une confirmation forte, une action qui renvoie un texte affiche ce refus), `ui/quoted` (« NOM » insécable), `ui/LabelForm` (un nom + son bouton : groupe, prénom), `ui/Sheet.module.css` (feuillets blancs et lignes de liste : membres, clés, appareils).
  - Serveur : `server/validate.ts` (contrôles d'entrée), `server/groups.ts` (`assertMember`, `getActiveGroup`).
  - Tests : `tests/helpers/movies.ts` (`aSnapshot`, `aMovie`, `NETFLIX`…), `tests/helpers/dom.ts` (`stubMatchMedia`), `tests/setup.ts` (nettoyage commun), mocks `vi.mock("@/server/session")` / `vi.mock("next/cache")` (dossiers `__mocks__`), `tests/helpers/functional.ts`, `tests/fake-tmdb/`, `e2e/fixtures.ts`.
- **Garde-fous automatiques** (ESLint, erreur = CI rouge) : 200 lignes max par fichier, 80 par fonction, complexité 10, imbrication 3, 4 paramètres max (sinon un objet), `===`, pas de ternaire imbriqué. **jscpd** refuse tout bloc dupliqué (6 lignes / 60 tokens), **knip** tout export ou dépendance inutilisé. Ne jamais contourner une règle (`eslint-disable`, seuil relevé) sans l'accord du mainteneur : découper plutôt.

## Définition de « fini »

1. Le comportement est testé au bon niveau : logique pure → test unitaire ; action serveur ou base → test fonctionnel (`tests/functional/`) ; parcours utilisateur → scénario e2e (`e2e/`).
2. `npm run ci` passe en local (le hook pre-push le relance de toute façon).
3. Tout changement d'UI est vérifié dans un vrai navigateur sur plusieurs formats. Les captures de référence (`e2e/visual.spec.ts`) le font automatiquement : un refactor ne doit en casser aucune ; un changement voulu se valide avec `npm run test:e2e -- --update-snapshots` puis en **regardant** les nouvelles images avant de les commiter.
4. Le `CLAUDE.md` et la spec sont à jour si une règle ou une version change.

## Conventions

- **Langue** : interface en français (MAJUSCULES pour titres et boutons, typographie française : « », espaces insécables) ; code et commentaires en anglais ; noms de tests en français (ils se lisent comme la spec).
- **DA « Ticket d'entrée » (riso fluo)** non négociable : papier `#fff4d6`, encre marine, rose, jaune et bleu fluo (texte encre sur le rose, pour le contraste), Archivo Black + Space Mono, contours épais, ombres décalées pleines. Aucune couleur brute hors `src/styles/tokens.css` (exception documentée : `src/features/pwa/brand.ts` pour les icônes).
- **Responsive** (spec §12) : téléphone d'abord ; `@media (min-width: 760px)` = écrans larges (nav en haut) ; `@container shell (min-width: 640px)` = colonne large (ticket couché, grille) ; hauteurs `520px` (téléphone couché), `620px`/`700px` (petits écrans). Vérifier tout changement d'UI dans un vrai navigateur sur plusieurs formats.
- Animations légères, `prefers-reduced-motion` respecté.
- **Commits** : `type(scope): description` ([Conventional Commits](https://www.conventionalcommits.org)), header seul, en anglais. **Le type fixe la version (semver)** : `feat` = fonctionnalité visible (mineure), `fix` = correction visible (correctif), `feat!` ou `fix!` = rupture (majeure) ; `refactor`, `test`, `ci`, `docs`, `chore` ne publient rien. Un commit = un type honnête : ne pas déguiser un refactor en `feat`. **Jamais de trailer `Co-Authored-By` ni de mention d'un outil d'IA.** L'agent du mainteneur peut commiter et pousser seul sur ce repo.

## Qualité et tests

- **CI locale** (lefthook, installé par `npm install`) : `pre-commit` formate et lint les fichiers indexés ; `pre-push` lance `npm run ci` (format, lint, types, doublons, code mort, tests + couverture, build + e2e, ~1 min). Ne jamais pousser au rouge ni contourner (`--no-verify`, `LEFTHOOK=0`) sans raison dite au mainteneur. GitHub Actions rejoue les mêmes vérifications en jobs parallèles puis déploie (voir « Pièges »). Dependabot ouvre chaque lundi une PR de mises à jour : la fusionner si la CI est verte.
- **Couverture** (`vitest.config.ts`, seuils 95/95/95/90, actuellement 100 %) : tous les `.ts` de `src/` sauf hooks et câblage, donc tout nouveau module y entre seul. `docs/coverage.md` est mis à jour à la main.
- **Tests UI** : Testing Library, requêtes par rôle et texte visible, pas de détails d'implémentation.
- **Tests fonctionnels** (`tests/functional/`) : `startServerStack()` donne une vraie base SQLite et le faux TMDB ; on appelle les vraies actions serveur. `withLeasGroup()` : avant chaque test, listes vidées et un groupe « NOUS DEUX » neuf pour Léa (l'utilisateur de la session mockée), lire `.id` dans le test ; `tests/helpers/groups.ts` (`aDatabase`, `aUser`, `aGroup`) pour les tests de dépôts.
- **E2E** (`e2e/`, Playwright) : toujours dans l'image Docker officielle Playwright (`scripts/e2e.sh`, Docker requis), pour que les captures soient identiques ici et sur GitHub ; build de prod et faux TMDB (`e2e/global-setup.ts`, port 3218), profils iPhone et desktop. **Tests en parallèle** : un serveur (port 3220 + n) et une base (`e2e/.data/e2e-n.db`) par worker (`e2e/env.ts` : 4 en local, 2 sur GitHub) ; un test ne doit donc rien partager hors de sa base. Toujours importer `test` depuis `e2e/fixtures.ts` (il fournit l'adresse du serveur du worker). La fixture `app` vide la base du worker et connecte Léa (utilisateur et session écrits en base, cookies donnés au navigateur), seule membre du groupe « NOUS DEUX » (`groupe-e2e`, cookie `ww_group` posé) ; `member(name)` connecte un autre membre de ce groupe sur un second appareil (son propre contexte de navigateur, fermé en fin de test) ; `myOtherDevice()` reconnecte Léa sur un second appareil, avec sa propre session (« TES APPAREILS », révocation) ; `outsider(name)` connecte, sur un second appareil, un compte sans groupe (qui ouvre un lien : « REJOINDRE ») ; `guest()` ouvre un second appareil déconnecté, avec un authentificateur de passkeys virtuel (créer son compte depuis un lien) ; `newcomer` connecte un compte sans groupe ; la fixture `visitor` vide la base sans session et donne au navigateur un authentificateur de passkeys virtuel (WebAuthn via CDP, Chromium, helper `virtualAuthenticator(page)`, exporté : `e2e/account.spec.ts` en donne un à chaque appareil de Léa pour ajouter une clé puis se connecter avec) pour les vrais parcours de connexion (`e2e/auth.spec.ts`) ; `swipe()` attend la fin des enregistrements (`settled`). `e2e/groups.ts` : pastille (`pill`, `createGroup`, `chooseGroup`), `openMembers`, `copyInviteLink` (le vrai lien, par le presse-papiers) ; pour les captures, `leasInvitation()` écrit un jeton fixe et `joinedOn(date)` fige « depuis le … », `leasAccountOn(date)` fige « MON COMPTE » (un iPhone et un Mac, une clé de chacun, dates fixes). L'e2e tourne en `SIGNUP=open` (`e2e/env.ts`) : le mode `invite` est couvert par les tests fonctionnels (`tests/functional/invite-signup.test.ts`). Ne jamais supprimer la base e2e pendant qu'un serveur la tient (`SQLITE_READONLY_DBMOVED`).
- **Accessibilité** : axe sans aucun défaut grave, contraste compris (WCAG AA). Sur le rose, le texte est en encre (`--on-pink`), jamais en blanc.
- Le faux TMDB (`tests/fake-tmdb/`) sert aux deux niveaux : un film utile à un test s'ajoute dans `catalog.ts`. L'appli le joint grâce à `TMDB_API_URL` (défaut : le vrai TMDB).

## Livrer une version

1. Section de spec, puis code par petites étapes testées et commitées.
2. Build local + vérification navigateur (`npm run start:local`).
3. Si le schéma change : `npm run db:generate`, migration rétrocompatible (voir plus haut) ; la CI la passera en prod.
4. `git push origin main` (la CI déploie), puis suivre le run : `gh run watch`.
5. **Versions : jamais à la main** (ni tag, ni `version.txt`). Le dernier job de la CI (`version`), une fois la prod vérifiée, lance release-please : si les commits poussés contiennent un `feat` ou un `fix`, il ouvre la PR « release » (`CHANGELOG.md`, `version.txt`), la fusionne aussitôt puis publie le tag `vX.Y.Z` et la release GitHub. Rien à approuver ni à fusionner ; ces fichiers de version ne relancent pas la CI (`paths-ignore`). Donc **un push = une version** s'il contient du visible : grouper les commits d'une même fonctionnalité dans un seul push.
6. Release note riso sur demande, hors du dépôt (une image PNG à copier-coller marche le mieux).
